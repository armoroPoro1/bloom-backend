# Bloom Health & Wellness — Backend 1.2.0

หลังบ้าน **Node.js + TypeScript + Fastify** สำหรับระบบลูกค้า ผู้ขาย แอดมิน และเนื้อหาสุขภาพของ Bloom

ชุดนี้มี API ที่ทำงานกับฐานข้อมูล SQL, migrations, seed, การยืนยันตัวตน, ตรวจสิทธิ์, จัดเก็บไฟล์, ชุดทดสอบ, Swagger/OpenAPI และเอกสารส่งต่อ โดยแยกจากหน้าบ้าน React เดิมตามคำขอ ยังไม่มีการแก้หรือเชื่อมหน้าบ้าน และไม่มีการ deploy ไปยังบริการภายนอก

## ส่งให้ Claude ทำ integration ต่อ

เริ่มจาก **[CLAUDE_INTEGRATION.md](CLAUDE_INTEGRATION.md)** ซึ่งระบุงานเชื่อม React → Node ทั้งระบบ ลำดับลงมือทำ environment สัญญาข้อมูล จุดที่ต้องแก้ในหน้าบ้าน และเกณฑ์ส่งมอบ ใช้ [PROMPT_FOR_CLAUDE.txt](PROMPT_FOR_CLAUDE.txt) เป็นข้อความเริ่มงานได้ทันที

ZIP นี้มี **source ของ Node server ครบชุดพร้อมเอกสาร integration** ส่วน React ให้ใช้ `Bloom-Frontend-Claude-Handoff.zip` หรือ repository เดิมที่ส่งให้ Claude เพิ่ม มี [แผนที่ไฟล์หน้าบ้าน](docs/FRONTEND_FILE_MAP.md) และ [checklist ตรวจรับ](docs/INTEGRATION_ACCEPTANCE.md) ให้แล้ว ทุกกรณีใน checklist เป็นงานที่ต้องทดสอบเมื่อเชื่อมจริง รุ่น backend ยังเป็น 1.2.0 และโค้ด runtime/tests/migrations ไม่ได้เปลี่ยนในรอบเพิ่มเอกสารนี้

## รุ่นและการอัปเกรด

รุ่น 1.2.0 เพิ่มการทำงานอีเมลและ maintenance อัตโนมัติ, คิวลบไฟล์ที่ลองใหม่ได้หลัง restart, ประวัติหลักฐานชำระเงินสำหรับผู้ซื้อ/แอดมิน และแก้เรื่อง session ที่ถูกเพิกถอนระหว่างเปลี่ยนข้อมูลบัญชี สิทธิ์ดูรีวิว/Wishlist และความแม่นยำของยอดรายงาน รายละเอียดรอบนี้อยู่ใน `docs/CHANGES_V3.md` ส่วนประวัติรุ่น 1.1.0 อยู่ใน `docs/CHANGES_V2.md`

มี **165 API operations บน 123 paths และ 37 ตาราง application ใน 6 migrations** รายการ API สร้างจาก OpenAPI โดยอัตโนมัติใน `docs/API_INDEX.md` และตารางเทียบ requirement อยู่ใน `docs/REQUIREMENTS_COVERAGE.md`

ถ้าเคยรันรุ่นก่อนแล้ว ให้สำรองข้อมูลและรัน `npm run db:migrate` ก่อนเริ่มรุ่นนี้: จาก 1.1.0 จะเพิ่ม migration 006; จาก 1.0.0 จะเพิ่ม 005 และ 006 ตามลำดับ รักษา migrations 001–005 เดิม ไม่ต้องลบฐานข้อมูลหรือรัน seed ทับข้อมูลเดิม ถ้าใช้ PGlite ให้หยุด API ที่ใช้โฟลเดอร์ฐานเดียวกันก่อนเรียกคำสั่ง migration แยก

## เริ่มรันบนเครื่อง

ใช้ Node.js 24 เพื่อให้ตรงกับสภาพแวดล้อมที่ใช้ตรวจโครงการ ไฟล์ lock กำหนด dependency ที่ติดตั้งไว้

1. เปิดโฟลเดอร์ที่มี `package.json`
2. ติดตั้ง dependency และคัดลอกไฟล์ตัวอย่าง environment

```sh
npm ci
cp .env.example .env
```

บน PowerShell ใช้ `Copy-Item .env.example .env` แทนคำสั่ง `cp`

3. ตั้ง `SEED_DEMO_PASSWORD` ใน `.env` เป็นรหัสผ่านสำหรับข้อมูลสาธิต ยาวอย่างน้อย 12 ตัวอักษร แล้วรัน:

```sh
npm run db:migrate
npm run db:seed
npm run dev
```

API: `http://localhost:4000`  
Swagger UI: `http://localhost:4000/docs/`  
OpenAPI ใน ZIP: `docs/openapi.json`

โหมดเริ่มต้นใช้ **PGlite แบบบันทึกลงไฟล์ใน var/database** จึงเริ่มทดสอบได้โดยไม่ติดตั้ง PostgreSQL หรือ Docker เพิ่ม เป็นฐานข้อมูลฝั่ง Node จริงและเก็บข้อมูลข้ามการเปิดโปรแกรม ไม่ใช่ localStorage ของเบราว์เซอร์ โหมดนี้ใช้สำหรับพัฒนา/ทดสอบ; production ใช้ PostgreSQL ผ่าน `pg`

ไฟล์รูปอยู่ใน `var/uploads` ทุกไฟล์ผ่านการ decode และแปลงเป็น WebP ก่อนบันทึก ส่วนอีเมลพัฒนาจะถูกส่งเป็นไฟล์ส่วนตัวใน `var/mail` ตามรอบ worker อัตโนมัติ โฟลเดอร์ `var` ไม่รวมอยู่ใน ZIP

ค่าเริ่มต้น `BACKGROUND_JOBS=true` ทำให้ API ใช้ database handle เดียวกันเพื่อประมวลผลอีเมลและ maintenance จึงทำงานกับ PGlite ใน process เดียวได้ แต่ละงานเริ่มตรวจทันทีหลังเปิด server และทำซ้ำตาม `MAIL_INTERVAL_SECONDS=10` (1–3600) กับ `MAINTENANCE_INTERVAL_SECONDS=60` (5–3600) งานชนิดเดียวกันไม่รันซ้อน ตรวจ migration ก่อนทำงาน และรอให้งานที่กำลังทำเสร็จก่อนปิดฐานข้อมูลเมื่อรับ SIGINT/SIGTERM

บัญชีตัวอย่างและ UUID อยู่ใน `scripts/seed.ts` โปรแกรม seed แสดงอีเมลที่ใช้ได้ แต่ไม่พิมพ์รหัสผ่าน และไม่ทับข้อมูลหรือรหัสผ่านที่มีอยู่แล้ว

## ใช้ PostgreSQL

มี `compose.yaml` สำหรับ PostgreSQL 17 ในเครื่อง หากมี Docker:

```sh
docker compose up -d db
```

ตั้ง `POSTGRES_PASSWORD` ก่อนเรียก Compose จากนั้นแก้ environment ของ API:

```dotenv
DATABASE_DRIVER=postgres
DATABASE_URL=postgresql://bloom:YOUR_LOCAL_PASSWORD@localhost:5432/bloom
```

URL-encode อักขระพิเศษในรหัสผ่านของ connection string แล้วรัน migrations/seed เช่นเดียวกัน ไม่ต้องเปลี่ยน business logic หรือ SQL schema การเปลี่ยน driver ไม่ย้ายข้อมูลจาก PGlite ไป PostgreSQL ให้อัตโนมัติ

รายละเอียด deployment, SMTP, migrations, backups และขอบเขตที่ตรวจแล้วอยู่ใน `docs/OPERATIONS.md` และ `docs/VERIFICATION.md`

## การชำระเงินและบริการภายนอก

การโอนเงินในระบบเป็น flow ตรวจหลักฐานโดยแอดมิน ระบบบันทึกผลตรวจจริงลงฐานข้อมูล แต่ไม่ยืนยันยอดกับธนาคารโดยอัตโนมัติ การคืนเงินบันทึกเหตุการณ์ที่ผู้ดูแลทำภายนอกแล้ว พร้อมเลขอ้างอิง โดย API ไม่ย้ายเงินจริง

`ALLOW_DEV_PAYMENTS=true` เปิดตัวเลือกชำระเงินสาธิตสำหรับ local/test เท่านั้น ค่าเริ่มต้นปิด และ production ปฏิเสธการเปิดตัวเลือกนี้

ระบบจัดส่งบันทึกเลขติดตามและสถานะจากร้าน ยังไม่เรียก API บริษัทขนส่ง ไม่มี payment gateway, SMS, social login หรือ object storage ภายนอกเชื่อมไว้ การส่งอีเมลจริงใช้ `SMTP_URL` ที่ผู้ดูแลตั้ง และประมวลผลผ่าน worker อัตโนมัติหรือคำสั่ง worker แยกตามการตั้งค่า

ออเดอร์โอนเงินที่ยังไม่ส่งหลักฐานมีเวลาเริ่มต้น 24 ชั่วโมง (`PAYMENT_RESERVATION_MINUTES=1440`) เมื่อหมดเวลาระบบยกเลิกและคืนสต็อกครั้งเดียว ออเดอร์ที่ส่งหลักฐานรอตรวจหรือจ่ายแล้วไม่หมดอายุด้วยงานนี้ หลักฐานที่ถูกปฏิเสธจะเริ่มช่วงเวลาใหม่ maintenance อัตโนมัติจัดการอายุออเดอร์ คิวลบไฟล์ และข้อมูลบัญชีที่หมดอายุ ถ้าตั้ง `BACKGROUND_JOBS=false` ต้องจัดให้มีคำสั่ง worker/maintenance ทำงานเป็นระยะ ส่วนออเดอร์ที่ยอดสุดท้ายเป็นศูนย์จะเป็น `no_charge` และไม่ต้องแนบหลักฐาน

หากวางหลัง reverse proxy ให้ตั้ง `TRUST_PROXY_CIDRS` เป็น IP/CIDR ของ proxy ที่เชื่อถือและเชื่อมถึง API โดยตรง ค่าเริ่มต้นว่างไม่เชื่อ forwarded headers ไม่รับ wildcard, `/0`, hostname หรือจำนวน hop และ proxy ต้องแทนที่ forwarding headers ที่ client ส่งมาเอง ตัวนับ rate limit ยังแยกต่อ process; รายละเอียดอยู่ใน `docs/OPERATIONS.md`

## คำสั่งหลัก

```sh
npm run typecheck
npm test
npm run build
npm start
npm run openapi
npm run mail:worker
npm run maintenance
```

`npm start` ใช้ไฟล์จาก build จึงต้องรัน `npm run build` ก่อน

`npm run openapi` สร้างทั้ง `docs/openapi.json` และ `docs/API_INDEX.md` จาก routes ปัจจุบัน ไม่ต้องแก้ index ด้วยมือ ส่วน `mail:worker` และ `maintenance` เป็นคำสั่งทำงานหนึ่งรอบแล้วจบ ถ้าใช้ PGlite ต้องหยุด API ก่อนเปิด process แยกที่ใช้โฟลเดอร์ฐานเดียวกัน; งานอัตโนมัติภายใน API ใช้ได้ตามปกติ

หากใช้ PostgreSQL สำหรับการทดสอบ ให้ตั้ง `TEST_DATABASE_URL` ไปยังฐานทดสอบโดยเฉพาะ แล้วรัน `npm test` ชุดทดสอบสร้างและลบ schema ชื่อสุ่มของตัวเอง รวมถึง fixture อัปเกรดฐานข้อมูลที่มีข้อมูลเดิมซึ่งเลือก driver ตามตัวแปรนี้แล้ว มี GitHub Actions workflow พร้อม PostgreSQL service ให้แล้ว จำนวน ผล และขอบเขตการทดสอบจริงอ้างอิง `docs/VERIFICATION.md`
